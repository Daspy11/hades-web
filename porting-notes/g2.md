# g2: Reactive.Banana.GI.ArrowDialog (GTK interpreter for gadget dialogs)

File: `src/banana-ui/gtk/src/Reactive/Banana/GI/ArrowDialog.ts` (tests: `ArrowDialog.test.ts`, 48
tests). Demo: `src/scratch/g2Demo.ts`, `http://localhost:5173/?demo=g2`
(`&dialog=test|notebook|cond|loop|matrix|run|none` picks the dialog opened at start-up; `test` is
the default). Every definition of the Haskell module is ported; every gadget constructor of
`Gadget` has a case in `renderGadget` (most in a `renderGadget_<Constructor>` function; the
`Optional` special cases are in `renderGadget_Optional`).

## API (import from `@/banana-ui/gtk/src/Reactive/Banana/GI/ArrowDialog` or `.../GI`)

* `mkGtkPopupSelect(parent: Gtk.Widget, iconTheme, env: Changes<E>, selector: DialogSelector_<E, W, A>, trigger: B.Event<readonly [K, A]>): B.Event<[K, Maybe<A>]>`
* `mkGtkPopup(parent, iconTheme, env: Changes<E>, trigger: B.Event<readonly [K, A, Dialog_<E, W, A>]>): B.Event<[K, Maybe<A>]>`
* `createDialog(parent, iconTheme, envC: Changes<E>, [key, initial, dialog]): B.Event<[K, Maybe<A>]>`
* `mkDialogWidget(iconTheme, newWidgetIO: (w: Gtk.Widget) => void, envInit, envC, selectorB: B.Behavior<DialogSelector<E, W, I, O>>, initial: readonly [K, B.Behavior<I>], inputE): [Gtk.Widget, B.Event<[K, O]>, B.Event<readonly W[]>]`
* `renderGadget(iconTheme, wInit, env, initial: GadgetData<I>, envC, e, b, gadget): GadgetOut<W, O>`
* `boxWidgets(wInit, orient: Orientation, ws): Maybe<Gtk.Widget>`, `cleanOutput(g)`.
* `GadgetOut` record (`gadgetView`, `gadgetEvents: B.Event<readonly W[]>`, `gadgetInitial`,
  `gadgetUser`, `gadgetValue`), constructor `GadgetOut(...)`, instances `fmap_GadgetOut`,
  `pure_GadgetOut`, `ap_GadgetOut`, `mempty_GadgetOut(memptyV)`, `append_GadgetOut(appendV, g1, g2)`.
* Re-exported as in Haskell: `GadgetData`, `gdOk`, `gdValue` (from `Reactive/Banana/Common`).
  Also exported for the tests: `displayClickables`, `GtkClickable`.

All of these except `runDialog` are synchronous `MomentIO` functions: call them while a network
is being built (`B.compile`, an `execute`d action, `B.liftMomentIO`). `createDialog` and the
popups show the dialog at once and return; the result event fires on a button response
(`Ok`/`Close` → `Just`, `Apply` → `Just` and the dialog stays, `Cancel`/window close → `Nothing`).

* **`runDialog(parent, iconTheme, dialog, env, initial): Promise<Maybe<A>>`** is async: it
  compiles and actuates its own network, awaits `Gtk.dialogRun`, pauses the network and destroys
  the dialog. Call it from IO code (`await runDialog(...)`), never from inside network building.
* The rank-N widget initialiser is `(w: Gtk.Widget) => void`; the parent of a dialog is any
  `Gtk.Widget` (its toplevel window becomes `transientFor`).

## Semantics other modules must know (faithful to the Haskell)

* **Display gadgets inside `form`/`box`/`grid`/`tabForm` must not be focused with an ordinary lens
  on a field that another gadget edits.** `mergeOutputs` merges every user edit with the *current
  value* of every other gadget of the group, and a display gadget's value is `set lens <old value>`,
  so it writes the old value back over the edit (e.g. `focusing id $ readOnlyText ...` next to
  editable fields makes them uneditable; the original `demo-arrow` "Range size" has this bug).
  HADES uses `nullLens = lens (const ()) const`; in TS use a lens whose setter ignores the value:
  `lens((s) => s.x, (s, _v) => s)`. The same applies to `message`, `imageDisplay`,
  `readOnlyMemo` and to two editors of the same field.
* `memoPopup`/`FixedMemo` with a nested dialog opens a popup for **every** button press (the
  Haskell does not filter the press event), so a double click opens three dialogs. `textPopup`
  (`FixedText`) correctly opens one on a double click.
* A text box does not emit invalid text, so the OK button of `runDialog`/`createDialog` stays
  sensitive while a typed text box holds unparsable text (validators produce `_gdOk = false`).
* `Loop`: initial values are built lazily (`LazyGadgetData`, own enumerable memoised getters),
  so a loop state is computed from the output of the gadget it feeds; forcing a value that
  depends on itself throws `renderGadget: <<loop>> ...`. Copies of lazy gadget data (`{...g}`,
  the `gdOk`/`gdValue` lenses, `fmap_GadgetData`) force the fields.

## Async (`// Web:`) restructurings

* Colour box / optional colour box: the colour chooser `dialogRun` runs asynchronously from the
  entry icon handler; the entry text is set (and the edit event fires) when it closes.
* `FilePathSelector`: a click starts the (async) native file chooser; the edited value event fires
  when it is closed (errors are shown with `errorBox`).
* `ButtonIO`: the click starts the action (which may return a Promise); the result event fires
  when it completes; exceptions show the Haskell error box text.
* `ImageDisplay`: the bytes are decoded asynchronously (`Gdk.pixbufReady`); the size check and
  scaling run then; superseded updates are dropped.
* `entryChangedSignal` connects to the entry's `changed` signal (emitted once per text change,
  user or programmatic) instead of the buffer's inserted/deleted-text pair.
* `ForestTable`: preferred sizes are measured again at the first allocation after the widgets are
  in the page, and the initial sizing is redone with them (GTK can measure before showing).

## Toolkit changes (src/lib/GI/Gtk)

* `Render.tsx` tooltips: widget tooltips never opened (the Radix `Tooltip.Trigger asChild` got no
  ref/props from the widget views). `withTooltip` now wraps the view in a `display: contents`
  span (no layout box; CSS child selectors on tooltip widgets would see the span) and shows a
  `.gtk-tooltip` below the widget's element after 600 ms, via a portal. `@radix-ui/react-tooltip`
  is no longer imported by `Render.tsx` (`RenderRoot` still mounts its provider).
* `Render.tsx` `BoxView`: a `GtkButtonBox` lays out its children in insertion order whatever their
  pack type, as GTK does; dialog buttons now read "Cancel, OK, Apply" left to right (they were
  reversed).
* `Render.tsx` `NotebookView`: all pages share one grid cell and inactive pages are
  `visibility: hidden`, so a notebook requests the size of its largest page (as GTK): tabbed
  dialogs no longer change size when the user switches tabs.
* `Render.tsx` `ButtonContent`: a button's child widget with `halign` fill gets the whole width of
  the button (a wrapping label with `xalign: 0` is left-aligned, as in GTK).
* `Render.tsx` `LabelView`: `maxWidthChars` is not applied as a CSS max-width when the label has an
  explicit allocation in a `Layout` (`widgetSizeAllocate`), so allocated labels use their width.
* `TreeView.ts`: `treeSelectionSelectPath`/`UnselectPath`/`SelectIter`/`UnselectIter` consult the
  selection function (as `_gtk_tree_selection_row_is_selectable`) and do nothing, without a
  `changed` signal, when the row is already in the requested state.

## Known gaps

* The table gadget's view (`mkTableView`, g1) sits in a scrolled window that does not propagate its
  natural width, so wide tables are clipped (scrolled) in narrow dialogs.
* `Radio`: in GTK, `radioButtonJoinGroup` deactivates the joining button, so the original shows
  the *first* radio button selected until the input behavior changes, whatever the initial value.
  The toolkit's radio group keeps the active button, so the port shows the initial value. (Toolkit
  semantics; `ArrowDialog.ts` calls the same functions as the Haskell.)
* `Loop` is as strict as the Haskell: any inner gadget that reads its initial input while it is
  built (most widgets, `cond`, `exec`, `getInitial`) forces the loop state, which is a `<<loop>>`.
  Only gadgets such as `arr`/`initially` that do not inspect the initial input can sit directly
  inside a loop.
* The file chooser path of `filePathSelector` is in the demo (Pictures tab) but was not driven in
  headless Chrome.
